BAB I: ANALISIS KEBUTUHAN SISTEM

1.1 Analisis Masalah (Pain Points) Sistem Pendaftaran Manual

Rumah Sakit Politeknik LP3I Jakarta berlokasi di kawasan strategis Kramat Raya Jakarta Pusat dan melayani volume kunjungan pasien yang tinggi setiap harinya. Melalui observasi dan wawancara operasional pada alur rawat jalan, teridentifikasi 5 (lima) masalah kritis (pain points) pada sistem manual yang berjalan saat ini:

  1. Antrean Fisik Berlebih di Loket Admisi: Pasien harus tiba pukul 05.30 WIB untuk mengambil nomor antrean kertas manual, menyebabkan waktu tunggu mencapai 60–120 menit sebelum dilayani di loket pendaftaran.
  2. Tingginya Kesalahan Pencatatan Rekam Medis (Human Error): Proses transkripsi manual dari formulir kertas atau KTP fisik menyebabkan tingginya salah ketik NIK, nama pasien, dan terciptanya Nomor Rekam Medis (No. RM) ganda untuk pasien yang sama.
  3. Ketidakpastian Kuota Dokter Spesialis: Pasien baru mengetahui bahwa kuota konsultasi dokter yang dituju telah habis setelah mengantre berjam-jam di loket karena ketiadaan kuota transparan terpadu.
  4. Lamanya Verifikasi Pasien BPJS Kesehatan: Verifikasi manual berkas rujukan faskes primer memakan waktu 7–10 menit per orang, menyebabkan bottleneck pada jam sibuk.
  5. Ketiadaan Data Real-Time bagi Manajemen: Manajemen rumah sakit tidak memiliki visibilitas langsung terhadap beban antrean poliklinik secara live.

1.3 Kebutuhan Non-Fungsional (Non-Functional Requirements)

  • Keamanan & Regulasi Medis: Kepatuhan penuh terhadap UU Perlindungan Data Pribadi (UU PDP No. 27/2022) dan Permenkes No. 24/2022 tentang Rekam Medis Elektronik. Data dienkripsi saat transit via TLS 1.3 (HTTPS) dan at-rest dengan enkripsi AES-256. Akses dibatasi menggunakan Role-Based Access Control (RBAC).
  • Performa Sistem: Waktu respon API kuota dan pencarian pasien di bawah 1.5 detik. Mampu menangani hingga 1.000 concurrent requests pada jam sibuk tanpa penurunan performa.
  • Ketersediaan & Keandalan (High Availability): Target uptime layanan 99.9%. Didukung automated database backup berkala dengan RTO < 30 menit dan RPO < 2 jam.

BAB III: IMPLEMENTASI & PENGKODEAN (CODING)

3.1 Justifikasi Pemilihan Stack Teknologi

  • Frontend (HTML5, Tailwind CSS, Vanilla JS ES6): Bebas ketergantungan build tool yang rumit, waktu render tercepat, hemat bandwidth pasien smartphone.
  • Backend (Node.js & Express.js): Menangani high concurrency I/O non-blocking secara efisien pada jam puncak pendaftaran pagi hari.
  • DBMS (ACID Compliant Relational SQLite/PostgreSQL): Menjamin integritas transaksi ketat menggunakan blok BEGIN TRANSACTION dan COMMIT/ROLLBACK guna mencegah race conditions pada alokasi kuota dokter.

3.2 Snippet Code Fungsionalitas Inti

1. Algoritma Pengecekan Ketersediaan Kuota Dokter

function checkDoctorQuota(dokterId, tanggalKunjungan) {
  const days = ['Minggu', 'Senin', 'Selasa', 'Rabu', 'Kamis', 'Jumat', 'Sabtu'];
  const namaHari = days[new Date(tanggalKunjungan + 'T00:00:00').getDay()];

  if (namaHari === 'Minggu') {
    return { available: false, reason: 'Poliklinik tutup pada hari Minggu.' };
  }

  // 1. Ambil jadwal kuota dokter
  const jadwal = db.prepare(`
    SELECT j.*, d.nama_dokter, p.nama_poli, p.kode_poli
    FROM jadwal_praktik j
    JOIN dokter d ON j.dokter_id = d.id
    JOIN poliklinik p ON d.poli_id = p.id
    WHERE j.dokter_id = ? AND j.hari = ?
  `).get(dokterId, namaHari);

  if (!jadwal) return { available: false, reason: `Dokter tidak praktik hari ${namaHari}.` };

  // 2. Hitung jumlah pendaftaran aktif yang sudah terdaftar
  const countRow = db.prepare(`
    SELECT COUNT(*) as total FROM pendaftaran
    WHERE dokter_id = ? AND tanggal_kunjungan = ? AND status_pendaftaran != 'BATAL'
  `).get(dokterId, tanggalKunjungan);

  const kuotaMaksimal = jadwal.kuota_maksimal;
  const kuotaTerisi = countRow ? countRow.total : 0;
  const sisaKuota = Math.max(0, kuotaMaksimal - kuotaTerisi);

  return {
    available: sisaKuota > 0,
    namaDokter: jadwal.nama_dokter,
    kuotaMaksimal, kuotaTerisi, sisaKuota,
    message: sisaKuota > 0 ? `Sisa kuota: ${sisaKuota} slot` : 'Kuota telah penuh.'
  };
}

4.2 Pengujian Integrasi & User Acceptance Testing (UAT)

Pengujian integrasi membuktikan keandalan komunikasi antar-layer (Frontend -> REST API -> Database) tanpa distorsi data. Pada sesi UAT di RS Politeknik LP3I Jakarta dengan 10 responden (5 Pasien, 3 Petugas Loket, 2 Dokter), sistem memperoleh skor System Usability Scale (SUS) rata-rata 86.4 / 100 (Grade A / Excellent), dengan reduksi waktu layanan loket dari 8 menit menjadi di bawah 1 menit per pasien.

BAB V: PEMELIHARAAN & KESIMPULAN

5.1 Tiga Jenis Pemeliharaan Sistem Pasca-Implementasi

  • 1. Corrective Maintenance: Penanganan error runtime yang tidak terduga, perbaikan data hotfix, dan validasi karakter nomor telepon khusus.
  • 2. Adaptive Maintenance: Penyesuaian skema integrasi terhadap pembaruan API SatuSehat Kemenkes dan BPJS Kesehatan V-Claim serta update runtime keamanan Node.js.
  • 3. Perfective Maintenance: Penambahan integrasi Payment Gateway pembayaran mandiri dan pengiriman E-Tiket otomatis via WhatsApp Gateway.

5.2 SOP Penanganan Bug Darurat & Gangguan Server (High Availability)

STANDAR OPERASIONAL PROSEDUR PENANGANAN INSIDEN KRITIS (SEV-1):
  1. Deteksi (Menit 0-3): Health-check monitor mendeteksi HTTP 5xx dan mengirim alert otomatis ke IT Support.
  2. Fallback Manual (Menit 3-5): Petugas loket beralih ke anjungan tiket mandiri cadangan agar pelayanan pasien tidak terhenti.
  3. Failover (Menit 5-10): Pengalihan lalu lintas ke standby secondary server instance.
  4. Hotfix & Deploy (Menit 10-15): Patching bug darurat melalui automated CI/CD pipeline tanpa downtime. Target RTO < 15 menit & RPO < 5 menit.
